# D016: E047 is the current tip: bs 1536, a 20 px warmup stage, then 32 px, 6.75 epochs, 5.27 s, 0.7550. E040, E043 and E047 show that cheap, low-fidelity steps cost almost nothing during the warmup phase but cost accuracy once the lr peaks. Raising the batch size from 1024 to 1536 for the whole run saved ~5% of time but cost ~0.2 pp, and a higher Muon lr did not win it back (E041, E046). The question is whether batch size should be scheduled across training phases. In short training runs, does the critical batch size grow over training, so that the batch can be ramped up (for example 1024 early to 2048-3072 late, or larger during the low-res stage)? How should the lr and momentum be adjusted at each switch, especially with orthogonalized or normalized optimizers like Muon? Would such a ramp cut the number of steps without the accuracy loss of a fixed large batch? Is the opposite (large batch early during the cheap low-res warmup, smaller later) better supported?

Request R016 (auto, after E047); 80 papers found, 11 relevant, 5 read in full, 19 verified claims; cost $0.94

## Batch-size scheduling: what the cards say

**Note first:** E048 (5.00 s, 0.7552, keep) is newer than E047, so the current tip is E048, not E047.

**Ramp-up is supported, but only in long, SGD/Adam regimes.**
- **C0215 and C0216** (LLM, AdamW, WSD schedule): the critical batch size grows as the loss falls, and a 2M→6M ramp beats a fixed 4M. **Untested here:** the tree has no batch-schedule node. Add one under H1.2.
- **C0213 and C0214** (ResNet-50 on ImageNet, 90 epochs): a ramp keeps accuracy, while a large batch for the whole run loses about 1.1 pp. This matches the direction of E041 (fixed bs 1536 cost ~0.2 pp). **Conditional:** that evidence comes from runs about 10x longer than ~7 epochs.

**Why a late ramp may backfire here.**
- **C0209 and C0221:** raising the batch is equivalent to decaying the lr, because the noise scale is lr/B. A late ramp is therefore roughly a sharper tail anneal.
- That is exactly what H1.6.2 tested, and E025 refuted it: decay-to-0 cost 0.51 pp because lookahead needs diverse tail iterates.
- **C0223:** past the critical batch size you still need lr decay. Keep the existing step schedule; don't swap it for batch growth.
- For Muon this equivalence is only partial. The update magnitude is fixed, so a bigger batch only removes direction noise. **Conditional.**

**How to set lr and momentum at each switch.**
- **C0218:** sqrt(B) lr scaling at the switches did not help, and a constant lr was better. This fits E046, where a higher Muon lr didn't win back the bs-1536 loss. Keep the Muon lr at 0.16 across switches, and keep the SGD group's per-sample-normalized lr. **Conditional:** that result is for AdamW on LLMs.
- **C0210 and C0212:** raising momentum together with the batch cost 0.5–1 pp. Leave Muon momentum at 0.8, or lower it; never raise it at a switch. **Conditional.**

**Large batch early (the opposite schedule).** No card supports it. Critical-batch-size theory says early large batches waste samples. In this loop, though, the warmup phase tolerates low-fidelity steps (E040, E043, E047), so a large early batch probably costs little accuracy. It also saves little time, because those low-res steps are already cheap. **C0225–C0227** (progressive resizing on pretrained ResNets) are too weak to inform H2.3.

**Suggested test (one change on E048):**
- Run bs 1024 through the low-res stages and the lr peak, 1536 in the middle of the decay, and 2048 for the last ~30%.
- Index all schedules by samples seen (progress fraction), not by step.
- Keep Muon lr and momentum unchanged at each switch.
- Warm up every full and partial shape in build() with channels_last tensors.
- Pre-register: if accuracy drops ≥0.2 pp, read it per C0209 as over-annealing (as in E025). The follow-up is then a smaller final batch, or a raised Muon tail floor while the batch is large.

A cheaper variant tests the opposite direction: bs 2048 only during the 20/24/28 px stages, then 1536.

## Claims
- C0215 (untested; H1.2.3, H1): Critical batch grows as loss falls; add a batch-ramp hypothesis node under H1.2.
- C0216 (untested; H1.2.3): Dynamic ramp beat fixed batch (LLM/AdamW); motivates ramp test on E048 instead of fixed bs 1536.
- C0214 (explains; H1.2.3): Large batch throughout is worse than a ramp; consistent with E041's -0.2 pp at fixed bs 1536.
- C0213 (conditional; H1.2.3): Ramp keeps accuracy in 90-epoch ImageNet; unverified at ~7 epochs.
- C0209 (conditional; H1.6.2, H1.2.3): Batch increase ~ lr decay; a late ramp is like a sharper tail anneal, which E025 showed hurts with lookahead. Pre-register this failure mode.
- C0221 (conditional; H1.6, H1.2.3): Same equivalence for SGD; only partial for normalized Muon updates.
- C0223 (conditional; H1.6): Keep the existing lr decay when ramping; don't replace it with batch growth.
- C0218 (conditional; H1.2.3, H1.2): Don't rescale lr at batch switches; consistent with E046, where a higher Muon lr didn't help.
- C0210 (conditional; H1.2, H1.2.3): Don't raise Muon momentum when the batch grows.
- C0212 (conditional; H1.2): Same: momentum increases with batch cost accuracy.
- C0225 (conditional; H2.3): Weak support for progressive resizing (pretrained, small datasets); no action.
