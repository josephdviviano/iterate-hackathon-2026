# E043 · I049 · H2.3.2

H2.3.2 (open, c=0.42): FixRes-style mechanism: low-res training costs little final accuracy because the closing 32 px phase only needs to re-fit BN running statistics and the head to the test resolution. With fast BN running-stat momentum (as in Fable and airbench94_muon), that phase can be shorter. Part of E020's gain over E015 may come from this, beyond seed luck.
H2.3 (supported, c=0.75): Progressive resizing (whole-image bilinear downsampling on a 20 -> 24 -> 28 -> 32 px ladder, with only the last ~4 epochs at 32 px) cuts step cost at little accuracy cost. Step cost concentrates in the high-resolution group-1 layers, so early epochs at low resolution are cheap, and the first epochs are insensitive to resolution down to 20 px.
H2 (supported, c=0.80): Time is mainly set by per-step throughput: how fast each training step runs on the A100 (precision, memory layout, compilation, data pipeline, FLOPs per step), independent of how many steps are needed.
Idea: Exploit and add margin by fixing a BN-statistics mismatch (D004 C0031/C0035). Lookahead copies the slow weights into the model at the end of training, but the BN running statistics were accumulated under the fast iterates, and the frozen block's stats under the detach regime. At the end of train(), after the final Lookahead sync, reset all BN running stats. Re-estimate them with cumulative averaging (momentum=None) from 6 forward-only batches of 1536 un-augmented, un-flipped 32 px training images (no_grad, fp16, channels_last). Draw the images with the trial-seeded generator, then restore BN momentum. Do the re-estimation pass in a small CUDA graph or compiled function warmed up in build on synthetic data, so its first call costs nothing extra in the timed region. Training data only; the test set is never touched. Change nothing else on E038. Run salt 0 and salt 1.
Expected (from the queue): Time rises by 0.04-0.07 s (+0.6-1%, about 6.73-6.75 s). The 2-salt mean rises 0.05-0.3 pp over the tip's 0.7527, centred near +0.15 pp (about 0.754). Keep it if the 2-salt mean is >=0.7545 and salt 0 is >=0.753; that margin then pays for the E037-style 28 px shift (-0.10 s) or extending the freeze to 28 px. If the gain is <0.05 pp, the running stats already match the slow weights: refute the BN-mismatch part of H2.3.2 and close the BN-stat lever.

accuracy 0.7557 (0.7549 / 0.7544 / 0.7577) vs E038 0.7546 (0.7550 / 0.7535 / 0.7554); time 6.77 s (+0.08 s for the re-estimation). Verdict: inconclusive (+0.11 pp: below the +0.15 support bar, above the refutation bar). Discarded: +1.2% time for a gain inside noise.
SURPRISE — reproducibility: the smoke test of the same code gave seed 0 = 0.7519, the official run 0.7549. Earlier smoke tests matched official runs exactly (E018, E020: same seed-0 accuracy), and E002/E003 were bit-identical. The likely cause is max-autotune (on since E006) and cuDNN benchmark-style kernel selection, which time candidates at build time and can pick different kernels from run to run, changing fp rounding and thus re-rolling trajectories. So 'identical code -> identical 3-seed accuracy' no longer holds; my pre-registration's 'same-trajectory comparison' premise was false, and the run-to-run noise of the official metric is itself ~0.1-0.3 pp per seed.

## Post-mortem
<!-- For failures and missed predictions: what you predicted, what happened, the root cause,
what the world model got wrong, the lesson. -->
Predicted [0.7495, 0.7540] from the seed-0 smoke test (-0.31 pp); got 0.7557. Root cause: I assumed the training trajectory is bit-reproducible across processes (true in E002/E003 before max-autotune). With max-autotune and timing-based kernel choice, two runs of identical code can pick different kernels, so the smoke-test trajectory was a different draw. The world model's 'accuracy is deterministic per seed set' fact is stale since E006. Lesson: a 1-seed smoke test is a sample, not a preview; never centre predictions on it. Treat each official run as a fresh draw with run-to-run noise even at fixed code.
