# E023 · I027 · H2.4

H2.4 (open, c=0.60): Per-step cost concentrates in the high-resolution group-1 layers (32x32 and 16x16). It is limited by memory bandwidth (training-mode BN, activation and pooling traffic at batch 1000-2000) rather than by FLOPs. So cheapening group 1 (fewer convs, earlier pooling, fewer BN/activation passes) cuts time more cheaply than cutting epochs, and widening low-resolution layers is nearly free.
H2 (open, c=0.65): Time is mainly set by per-step throughput: how fast each training step runs on the A100 (precision, memory layout, compilation, data pipeline, FLOPs per step), independent of how many steps are needed.
Idea: Explore the next group-1 cut, extending E009's depth cut. On E018, reduce group 1 from 2 convs to 1, keeping only the 32x32 whitening-output -> 128 conv followed by pool/BN/GELU, and removing the remaining 16x16 128->128 conv. Raise epochs from 9.5 to 10.25 to compensate. Also record a one-step torch.profiler breakdown (conv vs BN/activation/pool kernels per stage) in the smoke test, which tests H2.4.1.
Expected (from the queue): Per-step time -8 to -10% (one 16x16 conv, matching E009's 9%), so train time at 10.25 epochs is about 7.9-8.1 s (-1 to -3%). Accuracy 0.752-0.757: the cut probably costs more than E009's 0.29 pp because group 1 then has no 16x16 conv, recovered by about +0.7 pp from the extra epochs. It wins only if it is >=0.754 at <8.0 s. The profiler should show >=40% of GPU time in non-conv kernels at 32x32/16x16. If not, H2.4's memory-bandwidth mechanism is weakened.

## Pre-registration

Cost model: E009 showed the analogous cut saves ~9% per step -> full-res epoch ~0.77 s, low-res ~0.49 s -> 5 x 0.49 + 6.5 x 0.77 + 0.06 ≈ 7.5 s.
