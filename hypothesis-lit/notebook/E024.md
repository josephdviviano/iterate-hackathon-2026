# E024 · I029 · H2.5

H2.5 (open, c=0.50): Python and kernel-launch overhead from the multi-group optimizer step (Muon Newton-Schulz per parameter, Lookahead, separate SGD groups) costs a measurable share of step time that compile flags do not reach. Capturing the train and optimizer steps in a CUDA graph, with foreach-fused updates and Newton-Schulz batched across parameters, removes it.
H2 (open, c=0.65): Time is mainly set by per-step throughput: how fast each training step runs on the A100 (precision, memory layout, compilation, data pipeline, FLOPs per step), independent of how many steps are needed.
Idea: Exploit, cheapening the per-step Muon cost (~2 ms/step of GPU time per the E018 profile, the same at 24 and 32 px). On the E021 incumbent (2/3/3 net, Muon at batch 1536 with lr 0.205 and momentum 0.655, CUDA-graphed step, 5 epochs at 24 px + 5.75 at 32 px, 0.7552 @ 7.62 s), replace the 3-step Newton-Schulz with Turbo-Muon-style almost-orthogonal preconditioning followed by 2 NS steps (C0008/C0009). Before NS, rescale X's columns by 1/sqrt of the row sums of |X^T X|, inside the batched NS call. Keep the same NS coefficients for the 2 remaining steps, and keep lr, momentum and everything else fixed. Recapture both CUDA graphs in build. Log ms/step per phase.
Expected (from the queue): Muon time drops by about 0.3-0.45 ms/step over ~344 steps, so train time falls by about 0.1-0.15 s (-1.3 to -2%), to about 7.47-7.52 s. With preconditioning the accuracy change should be within ±0.15 pp of 0.7552, which is inside trajectory noise. Keep it if accuracy is >=0.7535 and time is >=1% lower. If accuracy drops by >0.25 pp, the 3rd NS step matters in this short schedule; close the NS-step axis.
Commit c32e159; tip at launch: E021 @ 9fc0095; run log: runs/E024.log

## Pre-registration
On E021 (0.7552 @ 7.62 s). Change: Newton-Schulz 3 -> 2 steps with Turbo-Muon-style AOL preconditioning (rows of X rescaled by 1/sqrt(rowsum |X X^T|) on the small side; the rescaled Gram matrix is reused in the first step, so the preconditioner costs no extra matmul). Same coefficients, lr, momentum.
Dev check on random Gaussian matrices: singular values after precond+2 steps are [0.67, 1.21] (mean 0.92) for 128x216 and [0.67, 1.01] (mean 0.76) for 576x5184, vs 3 plain steps [0.96, 1.20] (mean 1.15) on 576x5184 -> large layers get a ~1/3 smaller effective update at the same lr; plain 2 steps would be much worse (mean 0.47).
- Prediction: accuracy [0.7505, 0.7570]
- Prediction: time [7.45, 7.58]
- Prediction: complete [1, 1]
- Supports if: (H2.5) time drops >= 1% and accuracy >= 0.7535.
- Refutes if: accuracy drops > 0.25 pp (< 0.7527) — the 3rd NS step (or its update magnitude) matters.

## Contingencies
- If it lands in the predicted range and supports: keep.
- If it moves the right way but less than predicted (time drop < 1%): discard; Muon NS cost was not the matmuls but the elementwise/norm parts.
- If it moves the opposite way (accuracy < 0.7527): discard; consider precond + 3 steps only if the update-magnitude explanation is tested (e.g. raising lr ~1.3x) via a future idea.
- If it crashes: tail, fix.
