## E003: why the compiled run was slower (+1.5 s)

**What the loop's own data says.** E003 (12.07 s) and E004 (9.04 s) have exactly the same accuracy (0.74863). So the math was identical and only the timing changed. E004 differed only in its fix: build warmup now uses channels_last tensors (the "stride-guard fix"). E002 is the eager run at the same 10 epochs, at 10.55 s. Compared with it, E003 was about 1.5 s slower and E004 about 14% faster. The most likely explanation is a recompile that leaked into timed code. Build compiled the graph for contiguous (NCHW) inputs. Real channels_last data then failed Dynamo's stride guards, so `max-autotune` recompiled and re-autotuned inside `train`. The kernels themselves were not slower. This answers the first open crux: the cost was fixed and fixable. Inductor kernels are faster than eager cuDNN once warm.

**Literature (thin; no card covers stride or layout guards directly):**
- **C0004** (explains): GraphMend reports cold-start compile cost that differs sharply from steady-state performance (up to 26x cold vs 1.39x steady). That fits E003: a single cold compile under max-autotune can outweigh a whole run's steady-state gain. Use it as the reason to treat any compile inside the timed region as a serious bug.
- **C0003 / C0006** (conditional, untested here): graph breaks send execution back to eager Python with CPU-GPU syncs, and removing them speeds things up. E004 may still contain breaks, for example in the GPU augmentation, the LR schedule or the optimizer step. These would hurt more under the 4-CPU pin. Action: run `torch._dynamo.explain` on the train step. If it finds breaks, fixing them is a cheap follow-up under H2.2.
- **C0005** (untested): breaks are common, about 14% of real models. This is a prior for the check above, not evidence about this loop.
- **C0001** (conditional): compile cost for dynamic shapes depends on the setup (that card is about language models). It matters for E003's dynamic-batch eval. The 5 s eval limit has not failed so far, so no action is needed unless eval times creep up.

**Effects on the tree:**
- **H2.2.1** is now supported by E004 (−14% time, accuracy unchanged), which overrides E003~.
- **H3.1** is missing a mechanism. It mentions only *shapes*, but layout, stride and dtype guards also trigger recompiles. Widen H3.1 or add a child H3.1.2 for this. Also make leaks fail loudly in every future run: set `torch._dynamo.config.error_on_recompile=True` (or a `recompile_limit` of 1) after build.
- **Forecasting lesson:** none of W1–W4 put probability on a +1.5 s fixed leak. Compile experiments should carry an explicit "leak" branch in their prediction ranges.

## Claims
- C0004 (explains; H2.2.1, H3.1): Cold-start compile cost is far larger than the steady-state gain, so a max-autotune recompile triggered by the stride-guard mismatch inside train explains E003's +1.5 s, and E004's fix explains the recovery. Treat any compile inside the timed region as a bug and use error_on_recompile to catch it.
- C0003 (conditional; H2.2, H2.2.2): Graph breaks cause an eager fallback plus CPU-GPU syncs, which costs more under the 4-CPU pin. Run torch._dynamo.explain on the E004 train step to see if any remain.
- C0006 (conditional; H2.2): If explain finds breaks, removing them (augmentation, schedule, optimizer) should give extra per-step gain on top of E004.
- C0005 (untested; H2.2): Prior that graph breaks are common; motivates the explain check, but is not direct evidence about this loop.
- C0001 (conditional; H3.1, H3.1.1): Compile cost for dynamic shapes depends on the setup; relevant to the dynamic-batch eval compile. Act only if eval nears the 5 s limit.
