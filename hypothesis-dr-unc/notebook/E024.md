H4.4 (open, c=0.30): Batch size and steps: at ~10 epochs the run is limited by optimizer steps. A smaller batch (more steps per epoch at similar FLOPs) raises accuracy per epoch more than the lost GPU efficiency costs in time. Fable's CIFAR-10 record used batch 1536, which argues the other way.
H4 (open, c=0.60): The airbench96 CIFAR-10 hyperparameters were tuned for 37 epochs and are mis-tuned for a ~10-epoch 100-class run. Re-tuning regularization, schedule and batch size for the under-fitting regime raises accuracy at fixed epochs, which lets the epoch count be cut. E004 shows one re-tune can be worth more than an epoch (+1.26 pp, ~1.4 epochs).
Idea: Follow-up to E015, which showed the regime is sample-limited, not step-limited: going from batch 1024 to 768 left accuracy flat and cost +5% time. Test whether a larger batch buys throughput. On E012 (11 epochs, translate 2), change only the batch size, from 1024 to 1536. Keep the per-example LR and wd as airbench defines them (per-step LR x1.5), tie the schedule to the new step count, recapture the CUDA graph for the new shape in build, and handle the last partial batch the same way as now.
Expected (from the queue): Time -2 to -5%, to about 7.3-7.55 s (fewer, larger, better-utilized steps). Accuracy -0.05 to -0.35 pp, since there are ~33% fewer steps (~36 per epoch). If accuracy stays >= 0.753 and time falls >= 0.15 s, this is a new best and batch 1536 becomes the default. A time gain under 1.5% means the A100 is already saturated at 1024, which closes the batch axis.
