## Digest: E015 (batch 1024 → 768)

**Most likely this is a baseline mislabel, not a new mechanism. Check that first.**
E015's description says it starts from E004 (10 ep, 128/384/576, 8.94 s). But E012 (128/256/576, 11 ep, 7.70 s) was already the kept incumbent when E015 ran. E014 points the same way: it is also described as an "E004" change, and it changed only label smoothing, which cannot alter compute. Yet it took 7.71 s, which is E012's time almost exactly. If E014 and E015 both actually ran on the E012 base, E015 makes sense under W13 and W14:
- **Time:** 7.70 → 8.09 s (+5%). That fits "small batches add per-step overhead" with ~33% more steps.
- **Accuracy:** 0.7567 → 0.7563, flat. More optimizer steps at equal samples bought nothing. So the run is **sample-limited, not step-limited**, which refutes H4.4's premise.

**Action:** diff commit 25bf18e (and 4e42e25) against 6d40ead and 2905511 to see which widths and epoch count actually ran. If the base was E012, re-score E015 and E014 against E012, mark H4.4.1 refuted, and give the world models no "surprise" credit. If the base really was E004, run the H1.1.3 noise-floor rerun of E004 before believing a 0.85 s drop.

**What the literature offers (weak fit):**
- **C0044 (conditional).** Training throughput can peak at an intermediate batch size and fall at larger batches, so a smaller batch can be faster per sample. This was measured on edge CPUs (RPi, Jetson) with ResNet-18. It would explain a genuine E004-based speed-up only if the A100 had a similar throughput peak below 1024. Nothing here has measured that. Low priority: if the mislabel check fails, microbenchmark per-sample step time at batch 512/768/1024/1536 on synthetic data in build.
- **C0045 (conditional).** The cause it gives is activation memory for backprop growing with batch size. On an 80 GB A100 with a 32 px airbench net at batch 1024, activations are a few GB, far below the limit, so this cause almost certainly doesn't carry over. Any real GPU non-monotonicity would come from per-shape kernel or autotune choices (max-autotune and CUDA graphs are captured per shape). The tree has no hypothesis for that, and it isn't worth adding unless the per-shape microbenchmark shows it.

**Bearing on the tree:** No card speaks to the accuracy half of the question (steps vs. samples). The flat accuracy at +33% steps is the informative part: lower H4.4 confidence. Also flag that E014's LS-0.0 verdict (refutes H4.1) may have been measured on the wrong base.
